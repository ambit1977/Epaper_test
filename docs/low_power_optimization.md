# 超低消費電力化 仕様

電池駆動を実用的にするための低消費電力対策。ソフト → 軽改造 → ベアモジュール化の
段階アプローチで進める。

---

## 1. 現状の消費電力（実測前の見積）

| 項目 | 電流 | 時間/日 | 消費/日 |
|------|-----|--------|--------|
| Deep Sleep（ESP32-WROOM-32 単体） | ~50 µA | 23h 56m | 1.2 mAh |
| Deep Sleep（**DevKit 経由**、USB-UART/LED/LDO 込み） | ~3-5 mA | 23h 56m | 72-120 mAh |
| 起動〜画面更新（WiFi 接続、NTP、API、E-Paper更新） | ~100 mA | 15 秒 × 144 回 | ~60 mAh |

**DevKit のまま使うとほぼ Deep Sleep の消費電流が支配的**。
これは ESP32 本体ではなく **周辺チップ** が原因。

### 寿命試算（10分間隔起動、単4電池ベース）

| 構成 | 1日の消費 | アルカリ単4 (1200mAh) | エネループ単4 (750mAh) |
|------|---------|---------------------|----------------------|
| DevKit そのまま | ~130 mAh | **9 日** | 5 日 |
| + Phase 1（ソフト最適化） | ~75 mAh | 16 日 | 10 日 |
| + Phase 2（DevKit 軽改造） | ~30 mAh | **40 日** | 25 日 |
| + Phase 3（ベアモジュール） | ~15 mAh | **80 日** | 50 日 |

## 2. Phase 1: ソフトウェア最適化（即実装可）

| 対策 | 削減量 | 実装難度 |
|------|------|--------|
| WiFi 静的IP 設定 | DHCP 1-2秒 短縮 | 低 |
| BSSID/チャンネル指定 + RTC RAM キャッシュ | 接続 3-5秒 短縮 | 低 |
| WiFi.persistent(false) | フラッシュ書込み削減 | 低 |
| WiFi.setSleep(true) で modem sleep 有効化 | アクティブ時 -10mA | 低 |
| NTP は1日1回のみ（RTC で時刻保持） | 1秒 短縮 | 中 |
| CPU を 80MHz に降圧（描画時のみ 240MHz） | アイドル -10mA | 低 |
| データ取得失敗時は短時間でリトライ放棄 | 異常時の電池消費削減 | 低 |
| 全GPIO を入力プルアップ/プルダウンで明示 | 漂流電流削減 | 中 |

### 期待される起動時間
- 現状: 約 12-15 秒（WiFi 接続 5-8s + API 2s + 描画 5s）
- 最適化後: 約 5-7 秒（WiFi 1-2s + API 1s + 描画 3s）

## 3. Phase 2: DevKit 軽改造（半田作業 数箇所）

ESP32 DevKit V1 の Deep Sleep 中電流の主な原因と対策。

### 3-1. 電源 LED の除去

- 赤色 PWR LED が常時点灯（約 2 mA）
- 対策: **LED 横の抵抗（R8 等）を撤去** または **LED 自体を撤去**
- 効果: -2 mA

### 3-2. USB-UART チップ (CP2102/CH340) の電源カット

- DevKit の CP2102 は USB 非接続時も AMS1117 経由で給電される
- 対策（基板リビジョンによる）:
  - CP2102 の VCC ピン（pin 6 or 7）をパターンカット
  - もしくは VBUS と CP2102 の間にダイオードを入れる
- 効果: -2〜3 mA
- ⚠️ カットすると USB シリアル通信ができなくなる。書き込み時は別途 FTDI 等を使う

### 3-3. AMS1117 LDO の代替（任意）

- AMS1117-3.3 の quiescent current は約 5 mA
- 代替: **MCP1700-3302E**（Iq = 1.6 µA、SOT-23）
- ピン互換ではないので置き換えにはパターン改造が必要

### Phase 2 後の Deep Sleep 中消費電流
- 推定 **0.3〜0.5 mA**（90% 削減）

## 4. Phase 3: ベアモジュール構成（将来）

DevKit を捨てて ESP32-WROOM-32 モジュール単体で構成。

### 必要部品

| 部品 | 役割 |
|------|------|
| ESP32-WROOM-32 モジュール | メイン |
| MCP1700-3302E（または XC6206P332MR） | 3.3V LDO（Iq 1-3µA） |
| 10kΩ プルアップ抵抗 × 2 | EN, GPIO0 |
| 0.1µF + 10µF コンデンサ | 電源デカップリング |
| タクトスイッチ × 2 | EN（リセット）, GPIO0（BOOT） |
| 6ピン書き込み用ヘッダ | プログラム書き込み用 |
| FTDI USB-UART アダプタ | プログラム書き込み時のみ接続 |

### Deep Sleep 中消費電流
- ESP32-WROOM-32 単体: 約 10 µA（typical）
- + MCP1700 Iq: 約 1.6 µA
- **合計 ~12 µA**

## 5. 計測手段

### 段階1: 動作確認のみ
- USB 電源 + シリアル出力で起動時間と動作を確認

### 段階2: 平均電流計測（推奨）
- マルチメーターを **電池とESP32 の間に直列接続**（mA レンジ）
- 数分間の表示の **平均** を読む
- Deep Sleep 中の電流値も確認

### 段階3: 詳細プロファイル（任意、高価）
- Otii Arc, Joulescope などの専用ロガー
- µs オーダーで電流変化を記録
- 各動作（WiFi接続、NTP、API、描画、sleep）の消費を分解

---

## 6. 実装スケジュール

1. ⬜ Phase 1 ソフト最適化を `weather_display_dual_lp` として実装
2. ⬜ 通常版と低消費版で起動時間ログを比較
3. ⬜ マルチメーターで平均電流を計測
4. ⬜ Phase 2 の改造可否を判断（半田作業の必要性 vs 効果）
5. ⬜ 必要なら Phase 2 実施 → 再計測
6. ⬜ ケース印刷後の最終運用時間で Phase 3 を検討

## 7. 参考: Wake on RTC タイマー以外の wake source

将来的に必要なら：
- **タッチ wake**: T0-T9 ピンに導電パッド → 触れたら起動
- **GPIO wake**: ボタン押下で更新トリガー
- **ULP コプロセッサ**: ULP が条件監視、必要時のみメイン CPU を起こす（高度）

天気予報用途なら **タイマー wake のみで十分**。
